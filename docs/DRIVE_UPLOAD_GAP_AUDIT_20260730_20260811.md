## 判定方式

- 直接列出根目錄、9 個主要資料夾及 14 個子資料夾的內容；最大資料夾為 R06，共列得 485 個檔案，沒有只抽樣前幾筆。
- 依 `config_templates/drive_targets.template.yaml` 的實際 folder ID 對應 R01～R14，不以根資料夾顯示名稱猜任務。
- 依 planner 的輸出日期規則反推每個 `--today` 應產生的檔案。
- 人工上傳但語意相同的檔名視為已存在，避免誤報：
  - R09/R10 日期後附加四位時間，例如 `202607301124`。
  - R06 第六館舊名稱 `忠孝預防3F` 與正式名稱 `忠孝預防醫學3F`。
  - R03 的 `全部`／`僅新客` 舊命名差異，但必須位於 R03 專用 folder 且截止日相同。
  - R05 的 `商品課程服務明細表`／`課程服務明細表` 前綴差異，但必須位於 R05 專用 folder 且截止日相同。
- 月累積型檔名有兩個日期欄位，例如 `課程服務明細表-20260801-20260803-僅新客.xls`；第一個日期是月份起日，第二個日期才是報表截止日。稽核必須比對第二個日期與檔名結尾，不能用任意 substring，否則會把缺少 2026-08-01 截止檔的狀況誤判為已存在。
- `每月_關帳後` 與 `庫存紀錄表` 不是目前 RPA 的 daily Drive target；它們可作歷史旁證，但不會用來掩蓋 daily target folder 的缺檔。

## R14 補跑契約

- 缺 R14 的排程日為 2026-08-02、2026-08-03、2026-08-04、2026-08-05。
- 每個日期都必須依序執行同日期的 `R13 → W01 → R14`。
- R13 一般失敗時不可執行 W01/R14；唯一例外是 2.1.16 已寫入且日期、查詢起迄日完全相符的 `r13_no_report_data.json`。此時仍執行 W01/R14，但 R14 的本期領用量固定以 0 筆處理且留下警告，不得搜尋或使用 stale raw data。W01 失敗時仍不可執行 R14。
- Drive 裡缺 R13 也代表不能只補 R14；即使 Drive 有 R13，POS 主機本機未必仍保留同一份 raw data，補跑工具仍應重新產生同日期 R13。

## 執行邊界

- 僅使用 POSReportBot 2.1.20 或更新版本；2.1.13 已收斂單一任務未處理例外，2.1.14 加入失敗 evidence ZIP，2.1.15 將 NonR05/R05 分流，2.1.16 修復狀態檔短暫鎖定與 R13 明確零筆時的 R14 降級鏈，2.1.17 修復唯讀歷史狀態檔及兩階段報表過早判定預覽完成；2.1.18 再讓持續被 Windows 鎖住的 canonical state 改存 execution recovery 檔；2.1.19 修正 R03 頁碼跨 scope 誤判；2.1.20 依操作人員確認修正 R05 課程階段漏勾退費，並取消在點開其他條件前就宣稱二次篩選已被 POS 移除的錯誤判定。
- 目前 artifact 維持未簽章；補跑不需要 SHA1/PFX 憑證。
- 補跑期間必須持有 `Local\POSReportBot.AutomationBatch`，並讓各 child EXE 仍各自取得 `Local\POSReportBot.AutomationRunner`，避免凌晨排程或人工操作插入兩個歷史任務之間。

- 實際補跑後必須重新列 Drive folder，確認缺口檔案及 Drive file ID；僅有 EXE exit code 0 不是最終上傳證據。
